# Cloud Migration — Implementation Roadmap

This is a **living document**. It gets updated as each step is actually executed — with the decision made, the alternative considered, and any deviation from the plan. It is the companion to [`Server_Design.md`](Server_Design.md) (the target architecture) — this file is the *path* to get there from the current single-process codebase.

## Guiding principles

- **Prepare before building.** Cut the internal boundaries between the future services (API Gateway / WS Gateway / Matchmaker / Game Allocator / Game Server Shard) inside the current single-process server *before* touching Redis/NATS/PostgreSQL/Kubernetes at all.
- **No rewrites.** Each file, once written for a given step, should survive later steps unchanged in shape — later steps add (e.g. a new implementation of an existing interface), they don't restructure.
- **Encapsulation is preserved throughout.** Every new class knows only the interface below it, never the technology behind that interface (the existing `PlayerAccountStore` abstraction over SQLite is the model to repeat).
- **Ordered, not all-at-once.** Each step below is independently committable and testable. Small steps are fine; skipping ahead is not.
- **Alternatives are evaluated at execution time**, not decided in advance — each step has a "Decision Log" subsection filled in when that step is actually done.
- **Speed and smooth scaling matter more than cost.** When a step involves a speed-vs-precision tradeoff, that tradeoff is called out explicitly in its Decision Log.

## Phase 0 — Prep: cut the boundaries in the existing code

No protocol or network changes yet. Same single executable, same WebSocket, same external behavior (`test_websocket_integration.cpp` keeps passing unchanged) — the code is just reorganized to already match the future service boundaries.

### 0.1 — Extract `AuthService`
**Status:** Done
**Goal:** Pull the business logic (not the networking) out of `GameWebSocketServer::handleLogin` into a new class that depends only on `PlayerAccountStore&` + `LobbyRegistry&` — no knowledge of sockets.
**Files:** `server/auth/auth_service.hpp/.cpp` (new), `server/network/websocket_server.cpp` (shrinks to call `AuthService`)
**Why here:** Seed of the future API Gateway. `handleLogin` today is already nearly "pure" business logic aside from the final `state.socket->send(...)` — low-risk extraction.
**Decision Log:** `AuthService::login(lobbyId, username, password) -> AuthResult{success, rating, existingMatch}` — takes `GameRegistry&` too (not just accounts/lobby) so it can resolve a resumable match on successful login, matching what `handleLogin` used to do inline. `GameWebSocketServer::attachToMatch` and the actual `socket->send(...)` stayed in `websocket_server.cpp` — those are genuinely WS-Gateway concerns (the live connection), not auth logic. `server/CMakeLists.txt` needed a new `AUTH_SOURCES` glob (new top-level folder, not auto-collected). Unit tests added in `server/tests/unit/auth/test_auth_service.cpp` using a real `SqlitePlayerAccountStore(":memory:")` (same pattern as the integration tests) rather than a hand-rolled fake, so the wrong-password path is exercised for real.

### 0.2 — Extract `RoomsService`
**Status:** Done
**Goal:** Pull `handleCreateRoom`/`handleJoinRoom` logic into a class depending only on `GameRegistry&` + `PlayerAccountStore&`.
**Files:** `server/rooms/rooms_service.hpp/.cpp` (new), `server/network/websocket_server.hpp/.cpp` (shrinks to call `RoomsService`), `server/CMakeLists.txt` (new `ROOMS_SOURCES` glob, same pattern as `AUTH_SOURCES`)
**Why here:** Second seed of the future API Gateway.
**Decision Log:** `RoomsService::createRoom(username) -> CreateRoomResult{roomCode, match}` / `joinRoom(username, roomCode) -> JoinRoomResult{success, match}` — takes `Matchmaker&` too (not just `GameRegistry&`/`PlayerAccountStore&`) because `matchmaker_.dequeue(username)` ("opening/joining a room cancels any pending matchmaking search") is a business rule that belongs with the room logic, not the WS layer. `waitingByUsername_.erase(...)` (the WS Gateway's own bookkeeping of which raw socket is waiting) and `attachToMatch(...)` (touches the live socket/PlayerId, sends the network snapshot) stayed in `websocket_server.cpp` — same reasoning as `AuthService` in 0.1: those are genuinely WS-Gateway concerns, not room logic. `RoomsService` owns its own `Board templateBoard_` copy, matching the existing pattern (`Matchmaker` and `GameWebSocketServer` each already own their own copy).

### 0.3 — Introduce a thin `GameAllocator`
**Status:** Done
**Goal:** Add `GameAllocator::allocate() -> GameRegistry&`. Today it trivially returns the single existing in-process registry — no real allocation logic yet.
**Files:** `server/matches/game_allocator.hpp/.cpp` (new), `server/lobby/matchmaker.hpp/.cpp`, `server/rooms/rooms_service.hpp/.cpp`, `server/network/websocket_server.hpp/.cpp`, `server/server.cpp`
**Why here:** The most important seam to open early. When multiple shards exist later, only this function's internals change — no call site does.
**Decision Log:** Scoped deliberately to only the call sites that create a brand-new match — not every place that touches `GameRegistry`. `Matchmaker` (its only `GameRegistry` use is `createMatch` inside `tick()`) had `GameRegistry&` **replaced entirely** by `GameAllocator&`. `RoomsService` is mixed — `createRoom` is allocation (routed through `GameAllocator`), `joinRoom` is a lookup by an existing room code — so it kept `GameRegistry&` **and** gained `GameAllocator&` as two separate references, rather than forcing the lookup through `allocate()` too. `AuthService` and `GameWebSocketServer`'s own direct `GameRegistry` uses (`matchFor`, `updateAll`) are all lookups — left untouched. Existing-match lookup across shards (what `joinRoom`/`matchFor`/`AuthService`'s resume check will need once multiple shards exist) is explicitly a separate, unsolved problem — likely a routing/lookup mechanism from Phase 6, not this seam. Rippled mechanically (constructor signature change, no behavior change) into `server.cpp` and three test files: `test_matchmaker.cpp`, `test_rooms_service.cpp`, `test_websocket_integration.cpp`.

### 0.4 — Shrink `GameWebSocketServer` to pure routing
**Status:** Done (achieved as a byproduct of 0.1–0.3, no additional code needed)
**Goal:** `GameWebSocketServer` becomes routing-only: parse the raw message, identify its kind, delegate to `AuthService` / `RoomsService` / `Matchmaker` / `GameAllocator`. It no longer knows *how* login or room-joining work.
**Files:** `server/network/websocket_server.cpp/.hpp`
**Why here:** This makes it, in practice, the seed of the future WS Gateway — routing is its only remaining job.
**Decision Log:** Audited every handler line-by-line after 0.3. `handleLogin`/`handleCreateRoom`/`handleJoinRoom` already only route + manage live connection state (socket↔match wiring) + build responses — no embedded business logic. `handleGameMessage`/`handleClose` are inherently WS-Gateway concerns (message routing, connection-lifecycle/disconnect-grace) by definition, not domain rules being reimplemented. One candidate found: `handleFindMatch`'s `accounts_.ratingFor(username).value_or(1200)`. Deliberately **not** extracted — moving it into `Matchmaker::enqueue` would change its signature and ripple into ~24 call sites across `test_matchmaker.cpp`/`test_rooms_service.cpp` (several deliberately pass distinct explicit ratings to test the rating-range-matching boundary), for a fallback that in practice never triggers (every logged-in user already has a real rating from `loginOrRegister`). Disproportionate cost for near-zero value — logged here explicitly rather than silently skipped, revisit only if Phase 1 (REST) ever needs to trigger matchmaking from a second entry point.

### 0.5 — Unit tests for the new services
**Status:** Done — `AuthService` (0.1), `RoomsService` (0.2), and `GameAllocator` (0.3) all covered.
**Goal:** `AuthService`/`RoomsService`/`GameAllocator` get their own unit tests (no real socket involved) — additive to, not a replacement for, `test_websocket_integration.cpp`.
**Files:** `server/tests/unit/auth/test_auth_service.cpp`, `server/tests/unit/rooms/test_rooms_service.cpp` (5 cases: own match returned, roomCode joinable by a second player, matchmaking cancelled on both create and join, unknown roomCode fails cleanly), `server/tests/unit/test_game_allocator.cpp` (3 cases: allocate returns the constructed-with registry, repeated calls return the same registry, a match created via the allocated reference is visible through the original registry — i.e. allocate() really is just an indirection, not a copy)
**Why here:** Confirms the extraction didn't change behavior, and gives faster feedback than the full socket integration suite.
**Decision Log:** _(filled in when executed)_

**End-of-phase check:** same executable, identical external behavior, existing integration tests pass unchanged.

## Phase 1 — Split transport: real REST alongside WebSocket

**Status:** Done — `/health`, `/login`, `/players/{username}/rating` implemented, tested (native + Docker, both green). `createRoom`/`joinRoom` deliberately kept on WebSocket — see Decision Log for the resolved decision and its explicit future trigger.
**Goal:** Add a real HTTP listener (alongside the existing WebSocket, not replacing it) that exposes `AuthService`/`RoomsService`. This is the point where client↔API-Gateway and client↔WS-Gateway become two distinct network channels, not just two internal classes.
**Decision to make here:** ixwebsocket's built-in basic HTTP server vs. a dedicated REST library (e.g. cpp-httplib) — implementation speed vs. feature completeness.
**Decision Log:**
- Chose **cpp-httplib** over ixwebsocket's own HTTP support and over Boost.Beast. Deliberately picked for being **header-only** — after the hiredis/redis-plus-plus CMake integration fight in Phase 3 (exported-target include-directory rules, `find_path` not resolving a `FetchContent` source tree), a header-only library sidesteps that entire class of problem: there's no compiled library artifact to link against, only an include path, so there's effectively nothing for `FetchContent`'s `add_subdirectory` step to get wrong.
- Found a real design issue before writing code, not after: `AuthService::login(LobbyRegistry::ConnectionId, ...)` is inherently WS-connection-scoped (it records identity in `LobbyRegistry` and checks for a resumable match tied to a live connection) — neither operation is meaningful for a stateless REST call made before any WebSocket connection exists. Rather than force `AuthService` through REST, the new `POST /login` endpoint calls `PlayerAccountStore::loginOrRegister` **directly** (bypassing `AuthService` entirely) — the credential-check/rating part of login is genuinely stateless and REST-appropriate; the lobby-identify/resume-match part isn't, and stays exclusively on the WebSocket path (which is still how the client actually logs in for gameplay today — this endpoint proves the REST channel works, it doesn't yet replace anything).
- Same reasoning would apply even more sharply to `RoomsService` (`CreateRoomResult`/`JoinRoomResult` carry a `GameMatch*`, meaningless without a live connection to attach it to) — deliberately **not** exposed over REST in this pass.
- `Server` gained a second port (`httpPort_`, alongside the renamed `wsPort_`) — `main.cpp` now starts on 8080 (WebSocket, unchanged) and 8081 (HTTP, new).
- `HttpServer::start()` uses `bind_to_port()` + `listen_after_bind()` on a background thread (not the blocking one-call `listen()`) specifically so it can report bind failure via a `bool` return, matching `GameWebSocketServer::start()`'s existing contract.
- `/health` (plain `200 ok`) added alongside `/login`/`/players/{username}/rating` — near-zero extra cost now, useful later for Phase 7/8 container health checks.
- Tests added: `server/tests/unit/network/test_http_server.cpp` (7 cases) — real `HttpServer` + real `httplib::Client`, each `TEST_CASE` on its own port (same reasoning as `test_websocket_integration.cpp`'s per-fixture ports, to avoid `TIME_WAIT` flakiness). Covers `/health`, `/login` (new account, wrong password, malformed body, empty username), `/players/{username}/rating` (known, unknown). `docker compose up --build` re-run and confirmed green — httplib builds cleanly on Linux too.
- **Resolved (2026-07-31): `createRoom`/`joinRoom` stay on WebSocket, with an explicit future trigger to revisit.** The deciding factor isn't "REST is more professional for one-off actions" — that rule is too generic (`/login` is REST because it's genuinely session-independent; `createRoom`/`joinRoom` aren't, since they couple immediately into session lifecycle: `attachToMatch`, `PlayerRegistry` registration, live event flow). Two sides weighed:
  - *Keep on WebSocket (chosen for now):* `createRoom` → `attachToMatch` happens atomically on one connection, so there's no window where a room exists but nothing is attached to it — no orphaned-room TTL/cleanup needed. This matches today's reality: one server/shard, so there's no "which server should the client connect to" decision to make before opening the socket.
  - *Move to REST (correct once the condition below holds):* in a real multi-shard system, the client must learn *which* shard/server to connect to before opening a WebSocket at all — that decision belongs to something like `GameAllocator`, made before the socket exists, not after. Making it over an already-open WebSocket forces an awkward choice later (proxy through the wrong Gateway, or tell the client to disconnect and reconnect elsewhere); a REST call avoids this by design (`POST /rooms` → `{roomCode, serverAddress, token}` → client opens WS directly to the right target).
  - **Explicit trigger to revisit:** move `createRoom` to REST exactly when `GameAllocator` (the seam opened in 0.3) stops being a trivial single-shard passthrough and starts actually choosing between multiple real shards/servers (Phase 6) — not before. Doing it earlier means solving a routing problem that doesn't exist yet, at a real cost (client two-step flow, room TTL/cleanup) that does exist today. When the trigger hits, this is additive, not a rewrite: a new REST endpoint calling the already-decoupled `RoomsService` directly, same pattern as `/login` calling `PlayerAccountStore` directly — nothing built in this phase needs to change shape.

## Phase 2 — Durable storage: PostgreSQL

**Status:** Done
**Goal:** Implement `PostgresPlayerAccountStore`, matching the existing `PlayerAccountStore` interface exactly.
**Why here:** Lowest risk in the whole plan — the interface already exists and is proven (`SqlitePlayerAccountStore`). No call site changes.
**Decision Log:**
- `libpqxx` couldn't be installed natively on Windows via vcpkg — every MSYS2 mirror download failed with HTTP 418 from local network interference (antivirus/firewall). Pivoted to building/testing `PostgresPlayerAccountStore` inside a Linux Docker container instead (`apt-get install libpqxx-dev`), which sidesteps the blocker entirely rather than working around it.
- Getting Docker Desktop itself running on this machine (ASUS Vivobook, Windows) required a full round of virtualization troubleshooting: BIOS-level VT-x was already on, but `VirtualMachinePlatform`/`Microsoft-Windows-Subsystem-Linux`/`HypervisorPlatform` Windows features needed explicit enabling via `dism.exe`, plus `wsl --update` / `wsl --set-default-version 2`, plus a genuine full restart each time (not just closing/reopening a terminal). `wsl --install -d Ubuntu` succeeding was the actual confirmation the fix took.
- `server/Dockerfile` (new) and `docker-compose.yml` (new, repo root) run a `tests` service against a real `postgres:16` container — this is the project's first working Docker artifact, a small preview of Phase 8, done now only because it was the fastest way to unblock this phase.
- Git-in-container `FetchContent` for `ixwebsocket` failed with `server certificate verification failed` — same class of local network interference as the vcpkg issue. Worked around with `git config --global http.sslVerify false` inside the Dockerfile; flagged as a temporary tradeoff (build-time only, not runtime) pending a real root-cause fix (finding what's doing TLS interception and trusting its CA properly instead).
- Found and fixed a real portability bug unrelated to Postgres: `server/DB` (disk, uppercase) vs. `db` (every `#include`/CMake reference, lowercase) — silently fine on Windows' case-insensitive filesystem, fatal on Linux. Renamed via `git mv` (two-step, since plain `Rename-Item` refuses case-only renames).
- Found and fixed a second portability bug: `shared/logging/logger.cpp` used `localtime_s` (MSVC-only); added `#ifdef _WIN32` / `localtime_r` fallback for Linux.
- `PostgresPlayerAccountStore.hpp` originally forward-declared `namespace pqxx { class connection; }`, assuming modern libpqxx 7.x. Ubuntu 22.04's packaged `libpqxx-dev` is 6.4.5, where `connection` is a type alias, not a class — the forward declaration conflicted with the real header and cascaded into dozens of unrelated-looking parse errors. Fixed by `#include <pqxx/pqxx>` directly in the header instead of forward-declaring.
- `CMakeLists.txt`: added `pkg_check_modules(PQXX libpqxx)` (optional, not `REQUIRED`) so the Postgres store and its test file are silently excluded from the native Windows build (no `libpqxx` there) but included automatically inside the Linux container (found via `apt`'s pkg-config files). Needed the `PQXX_FOUND` include/link block added to **both** `KungFuChessServer` and `KungFuChessServerTests` — missing it on the second one caused a linker error (headers resolved via `/usr/include`'s default path, masking that the library itself was never linked).
- `docker-compose.yml`'s plain `depends_on: - postgres` only waits for the container to start, not for Postgres to finish `initdb` and accept connections — caused one flaky test failure (`Connection refused`) on the first successful build. Fixed with a proper `healthcheck` (`pg_isready`) and `depends_on: postgres: condition: service_healthy`.
- End state: `docker compose up --build` runs the full existing test suite (433 tests, including new `PostgresPlayerAccountStore` and `AuthService` tests) against a real containerized PostgreSQL — all passing.

## Phase 3 — Shared ephemeral state: Redis

**Status:** Done. `LobbyRegistry` pilot (`LobbyStore`/`InMemoryLobbyStore`/`RedisLobbyStore`), `GameRegistry`'s lookup indices (`GameIndexStore`/...), and `Matchmaker`'s waiting queue (`MatchmakerQueueStore`/...) all moved behind the same storage-interface pattern, each with a working Redis-backed implementation. `PlayerRegistry` turned out to be **out of scope** for this phase entirely — it's per-match, in-process state (a `GameMatch` member), not shared server-wide state; it only becomes a real Redis candidate once Phase 6 introduces multiple shards. `server.cpp` (the single-executable `KungFuChessServer` path) still wires every store in-memory — that's fine and expected, since it's still one process; `matchmaker_main.cpp`/`ws_gateway_main.cpp` (the actual Phase 5 split processes) are what use the Redis-backed stores for real.
**Goal:** Move the small, serializable pieces of in-process state — `LobbyRegistry`'s connection/identity map, later `Matchmaker`'s waiting queue and `PlayerRegistry`'s color assignments — into Redis-backed implementations, behind the exact same public interfaces the callers already use.
**Why here:** Only safe because Phase 0 already made these clean classes with clear interfaces — this becomes a technical swap, not a redesign.

**Scope correction (important):** not everything in these classes is a Redis candidate. `GameRegistry::matches_` holds `unique_ptr<GameMatch>` — live, actively-ticking game objects with a background thread driving them (`updateAll`), not inert data. Those cannot be serialized into Redis and keep running; sharing active games across processes is a Phase 5/6 problem (real Game Allocator + shards), not this phase. Only `GameRegistry`'s lookup indices (`usernameToGame_`, `roomCodeToGame_`, both simple `string → GameId`) are in scope here, and only once a pilot on simpler state proves the pattern.

**Pilot: `LobbyRegistry` first.** Smallest and simplest of the four — no dependency on `GameMatch`, no `chrono::time_point` fields to serialize (unlike `Matchmaker`/`PlayerRegistry`, which have timeouts/grace periods to think through separately). Design (mirrors the `PlayerAccountStore` pattern exactly):
- New `LobbyStore` interface (`server/lobby/lobby_store.hpp`): owns only the data (`nextConnectionId`, `addConnection`/`removeConnection`/`hasConnection`, `setIdentity`/`identityFor`). `LobbyRegistry` keeps its own orchestration logic (the `onIdentified` callback) and delegates storage to an injected `LobbyStore&`.
- `InMemoryLobbyStore` — today's behavior, unchanged, becomes the default (`LobbyRegistry`'s no-arg constructor keeps working exactly as-is, so no existing test or call site changes).
- `RedisLobbyStore` (new) — same interface, backed by `sw::redis::Redis`. Connection ids are allocated via Redis `INCR` (not a local counter) specifically so ids stay unique across however many processes share the store — otherwise two Gateway processes would hand out colliding ids.
- `LobbyRegistry(LobbyStore& store)` constructor added alongside the existing default one, so `server.cpp` can opt in later without forcing the change now (same "build it, prove it, wire it in later" approach already used for `PostgresPlayerAccountStore`).

**Decision — hiredis vs. redis-plus-plus (revised after trying both):** started with redis-plus-plus for its higher-level API (same reasoning as pqxx over raw libpq in Phase 2), but its CMake integration does `find_path(HIREDIS_HEADER hiredis)` / `find_library(HIREDIS_LIB hiredis)`, which expects an *installed* hiredis layout (`include/hiredis/hiredis.h`, nested). `FetchContent`'s source tree is the raw repo (flat — `hiredis.h` at the root), so the search failed (`HIREDIS_HEADER-NOTFOUND`) even though hiredis itself built cleanly via `FetchContent`. Rather than work around redis-plus-plus's CMake with a symlink/shim (fragile on Windows), switched to hiredis's raw C API directly — smaller dependency surface, and already proven to build cleanly in the same tree. `RedisLobbyStore` still hides this behind the same `LobbyStore` interface, so nothing outside `redis_lobby_store.cpp` is aware hiredis is a C library.
**Decision — how to build it:** `FetchContent` for `hiredis` only (same pattern as `ixwebsocket`/`sqlite3`), tried on native Windows first — this worked, unlike Phase 2's pqxx, which was forced into the pkg-config/Docker-only route because vcpkg was network-blocked and libpq itself isn't FetchContent-friendly. `hiredis` is a plain CMake GitHub project, and its `FetchContent` build succeeded natively on the first attempt.

**Known limitation — flagged before implementation, not discovered after:** moving `LobbyRegistry` to Redis is *not* by itself sufficient to allow multiple server instances. It only makes one piece of state (who's connected, who's identified) shared. Still unaddressed, and deferred to later phases:
- **Cross-instance coordination** (locks, Pub/Sub, or similar) for anything that today assumes "only one process is deciding" — e.g. `Matchmaker` pairing two waiting players must not double-pair them if two Matchmaker instances both see the same queue. This is Phase 4 (NATS) territory, or a Redis-native mechanism (`WATCH`/Lua scripts, Redis Pub/Sub) evaluated at that point.
- **Active game management across instances** — once `GameMatch` objects themselves need to be reachable from any process (not just their lookup index), that's the real Game Allocator + shard-routing problem (Phase 5/6), not a Redis data swap.
- **In-process callbacks stay in-process.** `LobbyRegistry::onIdentified_` is a `std::function` — it fires only within the process that called `identify()`. A second process reacting to "someone in Gateway A just logged in" needs actual cross-process delivery (Pub/Sub, Phase 4), not this pilot.

This phase's pilot is a correct, low-risk first step — proving the storage-interface pattern extends beyond accounts — but it is explicitly not a complete distributed-architecture solution on its own.

**Why `Matchmaker`/`PlayerRegistry` were next in line but not safe to move at the time (found while scoping the next step, 2026-07-30):** the real dividing line isn't data shape (e.g. having a `chrono::time_point`) — it's whether an operation reads a *set* of candidates and makes an *exclusive* decision among them. `LobbyRegistry`'s operations (register, identify, add/remove membership) are all independently atomic CRUD — safe to share via Redis with zero extra coordination, which is exactly why the pilot worked cleanly. `Matchmaker::tick()`'s pairing (scan all waiting players, pick two, remove both, create a match) and `PlayerRegistry::tryResumeSession` (check a pending disconnect, claim it) are the opposite: if two Matchmaker/PlayerRegistry instances both acted on the same shared Redis state concurrently, they could double-pair the same two players or double-resume the same seat. Moving their storage to Redis today would be *silently* correct (single process, so the race can't trigger) but a latent bug the moment Phase 5 introduces a second process. Not moving them until there's a real coordination mechanism (Redis-native — `WATCH`/Lua scripting for atomic read-and-claim — or NATS/Phase 4) is a deliberate decision, not a skipped task.

**Update (2026-08-10):** Phase 5 shipped exactly the coordination mechanism this note was waiting for — `MatchmakerServer` is now a genuine single OS process, so `Matchmaker::tick()`'s pairing race can't trigger at all, not just "doesn't trigger yet." `Matchmaker`'s queue moved to `MatchmakerQueueStore`/`RedisMatchmakerQueueStore` on that basis (see Decision Log). `PlayerRegistry` turned out to be a different case entirely, not just "still waiting its turn" — see the Decision Log entry below for why it's out of scope for this phase, not merely deferred.

**Decision Log:**
- Step 1 (`LobbyStore`/`InMemoryLobbyStore`) done. New files: `server/lobby/lobby_store.hpp`, `server/lobby/in_memory_lobby_store.hpp/.cpp`. `LobbyRegistry` rewritten to delegate to `LobbyStore&`, with its default constructor now owning an internal `InMemoryLobbyStore` — so `LobbyRegistry lobby;` (used throughout `test_lobby_registry.cpp` and `server.cpp`) keeps compiling and behaving identically; zero test or call-site changes needed. No `CMakeLists.txt` change required — `server/lobby/*.cpp` was already globbed.
- Found and fixed a lock-scope issue while doing this extraction (same class of bug as the earlier mutex audit): the original `LobbyRegistry::identify()` held its mutex for the entire function, including the call to the external `onIdentified_` callback. The rewritten version copies the handler under a brief lock and invokes it outside the lock.
- Connection-id allocation was pulled into `LobbyStore::nextConnectionId()` (rather than staying a `LobbyRegistry`-local counter) specifically so a future `RedisLobbyStore` can make it atomic across processes via Redis `INCR` — a local counter per process would otherwise hand out colliding ids once more than one process shares the store.
- Tests added: one case in `test_lobby_registry.cpp` covering the previously-uncovered `LobbyRegistry(LobbyStore&)` injection constructor, plus a new `server/tests/unit/lobby/test_in_memory_lobby_store.cpp` (8 cases) testing `InMemoryLobbyStore` directly against the `LobbyStore` contract — same precedent as `test_sqlite_player_account_store.cpp` testing its store directly rather than only through `AuthService`. Written so the same contract-level cases can be reused against `RedisLobbyStore` once it exists.
- Step 2 done: `RedisLobbyStore` (`server/lobby/redis_lobby_store.hpp/.cpp`, raw hiredis — see the hiredis-vs-redis-plus-plus note above), `redis` service added to `docker-compose.yml` (image `redis:7-alpine`, `pg_isready`-style healthcheck via `redis-cli ping`), `tests` service now depends on both `postgres` and `redis` being healthy.
- Found and fixed a real bug: `target_include_directories(hiredis PUBLIC ${hiredis_SOURCE_DIR})` (added defensively, to guarantee the include path reached our targets) broke the Docker/Linux build with `CMake Error: Target "hiredis" INTERFACE_INCLUDE_DIRECTORIES property contains path ... which is prefixed in the build directory`. Cause: hiredis's own `export(EXPORT hiredis-targets ...)` call makes `hiredis` an exported target, and CMake forbids an exported target's interface include directories from containing a raw (non-generator-expression) path inside the build tree. hiredis's own `CMakeLists.txt` already does this correctly (`TARGET_INCLUDE_DIRECTORIES(hiredis PUBLIC $<INSTALL_INTERFACE:include> $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}>)`), so the defensive line was both redundant and broken — removed entirely. Didn't surface on the native Windows build because `cmake -S ... -B ...` and `cmake --build ...` were run as separate commands there (the Generate-step failure didn't block the later build step, unlike Docker's `&&`-chained `RUN`, which fails hard on the first nonzero exit code).
- Found and fixed a minor build-hygiene issue: hiredis registers its own internal `hiredis-test` (via `test.sh`, a bash script) as a CTest test regardless of the `DISABLE_TESTS` option's expected effect — it isn't runnable through `ctest` on Windows and isn't our code. Disabled explicitly with `set_tests_properties(hiredis-test PROPERTIES DISABLED TRUE)` rather than relying on that option.
- Testing gate: unlike `PQXX_FOUND` (auto-detects whether libpqxx is installed), `hiredis` always builds via `FetchContent` — there's no absence to detect, only a real Redis instance to be reachable or not. Added an explicit `option(REDIS_TESTS ... OFF)` instead; `test_redis_lobby_store.cpp` (new, same shape as `test_postgres_player_account_store.cpp`) is excluded from `TEST_SOURCES` unless `REDIS_TESTS=ON`, so a native `ctest` run (no Redis reachable) isn't broken by it. `server/Dockerfile`'s `cmake` configure step now passes `-DREDIS_TESTS=ON`, so the real integration test only runs there, against the `redis` Compose service.
- **`GameRegistry`'s lookup indices moved next (2026-07-31)**, per the Phase 3 scope correction above: only `usernameToGame_`/`roomCodeToGame_` (both `string -> GameId`) are in scope, not `matches_` itself. Kept the original's safety property (only remove an entry if the store still points at the finished game, guarding a theoretical reorder where a username was already reassigned) via one extra lookup before each removal.

## Phase 4 — Inter-service channel: NATS

**Status:** Done — `NatsPublisher` implemented and tested (native no-throw behavior; gated `NATS_TESTS` real publish-then-receive round trip). `GameMatch` now mirrors its real `GameOverEvent` to NATS (`game.events.game_over`) via `NatsEventMirror`, alongside the existing periodic `server.heartbeat`.
**Goal:** Publish to NATS alongside the existing in-process `EventBus` (not replacing it yet) — proves the inter-service protocol works before anything depends on it.
**Decision to make here:** NATS core (plain pub/sub) vs. JetStream (persistence) — see `Server_Design.md` §4.
**Decision Log:**
- Chose **NATS core**, not JetStream — nothing depends on delivery/persistence guarantees yet; JetStream's streams/consumers/ack semantics aren't justified until something real needs them.
- `nats.c` via `FetchContent` (`NATS_BUILD_STREAMING`/`NATS_BUILD_WITH_TLS`/`NATS_BUILD_EXAMPLES` all `OFF`, minimizing what has to build) — same playbook as `ixwebsocket`/`hiredis`/`httplib`. Target name `nats_static` — best guess, to be confirmed once actually built (same caveat as every new `FetchContent` dependency this session).
- **Critical design difference from `PostgresPlayerAccountStore`/`RedisLobbyStore`:** those are required data stores — safe to throw on connection failure, since the server genuinely can't function without them once selected. `NatsPublisher` is an experimental side-channel that nothing depends on yet; it must **never** throw. Connection failure (construction) and publish failure (per-call) are both logged via `Logger::warn` and swallowed — `isConnected() == false` / a failed `publish()` leaves the server's actual gameplay completely unaffected. This was caught and fixed in review (an earlier draft silently discarded the `natsStatus` return value of `natsConnection_Publish` entirely — no way to tell publish failures from silent success).
- Initially deferred wiring into `GameMatch`/`GameOverEvent` (started with just the `server.cpp` heartbeat instead) — completed once the basic connectivity was proven. The ripple was minimized using the same own-vs-injected pattern as `LobbyRegistry`/`LobbyStore`: `GameRegistry` gained two constructors — a default one that owns its own disconnected `NatsPublisher` (today's behavior, unchanged, so every existing `GameRegistry registry;` test call site kept compiling with zero changes), and an injected one (`GameRegistry(NatsPublisher&)`) used only by `server.cpp`. `GameMatch`'s constructor gained a `NatsPublisher&` parameter, used to construct a new `NatsEventMirror` member (mirrors `RatingUpdater`'s shape exactly — subscribes to `GameOverEvent` on the match's own `bus_`). Only `test_game_match.cpp` (constructs `GameMatch` directly, 6 call sites) needed a mechanical update, using `NatsPublisher`'s new no-arg/disconnected constructor.
- Centralized event-to-wire serialization while wiring this up: found `NetworkPublisher` already had its own private `envelope(typeName, event)` helper (`{"type", "payload"}` JSON, then `.dump()`) — duplicating it inside `NatsEventMirror` would have produced two different serialization shapes for the same events. Moved `envelope` into `event_serialization.hpp` itself as a shared `toEnvelopeJson<EventT>(typeName, event)` template; `NetworkPublisher` and `NatsEventMirror` both use it now — one place to update if an event's structure ever changes, and NATS/WebSocket now emit the identical envelope shape for the same event.
- Found and fixed the same class of header-layout mismatch as hiredis: `nats_static`'s `target_include_directories` (correctly wrapped in `$<BUILD_INTERFACE:>`/`$<INSTALL_INTERFACE:>`, so no exported-target CMake error this time) points at `natsc-src/src`, where `nats.h` sits flat — the nested `nats/nats.h` layout only exists after `install()`. Fixed by including `<nats.h>` directly instead of `<nats/nats.h>`.
- Hit a Windows/MSVC-specific error comparing `unique_ptr<natsConnection, ConnectionDeleter> != nullptr` (`C2678`, pointing into the Windows SDK's `guiddef.h` — an operator-lookup collision unrelated to our logic). Fixed by using `unique_ptr`'s own `explicit operator bool()` (`static_cast<bool>(connection_)`) instead of comparing to `nullptr` directly, sidestepping whatever operator MSVC was trying (and failing) to resolve.
- Found and fixed the actual root cause of the `unique_ptr`/`guiddef.h` error above (the `operator bool()` fix helped but wasn't the real problem): `nats.h` declares `typedef struct __natsConnection natsConnection;` — `natsConnection` is a **typedef alias**, not a struct tag. The header's forward declaration (`struct natsConnection;`) created an unrelated, incompatible type by the same name, causing `error C2371: redefinition; different basic types` once the real `<nats.h>` was seen in the `.cpp`. Fixed by matching the real shape: `struct __natsConnection; typedef struct __natsConnection natsConnection;` — the same forward-declare-an-opaque-C-typedef pattern needed anywhere a C library hides its handle type behind a typedef instead of exposing the tag name directly.
- nats.c registers its own ~100-test internal suite (many requiring a real NATS/STAN server) as part of `FetchContent`, gated behind the standard CMake `BUILD_TESTING` variable — not a library-specific option like hiredis's `DISABLE_TESTS`. Fixed the same way in spirit as `hiredis-test`: `set(BUILD_TESTING OFF CACHE BOOL "" FORCE)` right before fetching `natsc`, scoped so it doesn't affect our own `KungFuChessServerTests` (driven by `enable_testing()`/`add_test()`, independent of `BUILD_TESTING`).
- `docker-compose.yml` gained a `nats` service (`nats:2-alpine`, monitoring port `8222` enabled via `-m 8222` for the healthcheck); `tests` now depends on `postgres`, `redis`, **and** `nats` all healthy.
- Tests added: `server/tests/unit/bus/test_nats_publisher.cpp` (3 cases, always built, no real NATS needed — connects to an unreachable address to verify the never-throws/no-op-when-disconnected contract) and `server/tests/unit/bus/test_nats_publisher_integration.cpp` (1 case, gated behind a new `NATS_TESTS` option — same reasoning as `REDIS_TESTS` — real publish-then-receive round trip: subscribes via raw `nats.c` first, publishes via `NatsPublisher`, confirms the message actually arrives). `server/Dockerfile`'s `cmake` configure now also passes `-DNATS_TESTS=ON`.
- Added `server/tests/unit/bus/test_game_match_nats_integration.cpp` (gated behind `NATS_TESTS` too) once `GameMatch`→`NatsEventMirror` wiring was done: builds a real `GameMatch`, drives it to an actual king capture (real `GameOverEvent`, not a synthetic payload), and asserts the message was actually received on `game.events.game_over` via a raw `nats.c` subscriber — closes the gap the generic publish/subscribe test left (that one proved `NatsPublisher` works, not that a real domain event reaches NATS end to end).

## Phase 5 — Actual process/container split

**Status:** Done — 5.1, 5.2, 5.3a, 5.3b, 5.4 all complete, verified natively and in Docker (see Decision Log). Three real processes (`ApiGateway`, `WsGateway`, `MatchmakerServer`) run and correctly talk to each other, proven by a real cross-process matchmaking test, not just "all three start."
**Goal:** Split the current single executable into three real processes, matching `Server_Design.md` §2/§3 at local/dev scale (one shard, one gateway per component):
- **API Gateway** — `HttpServer` + `PlayerAccountStore` only (`/login`, `/players/{username}/rating`, `/health`). Genuinely stateless already.
- **WS Gateway + Game Shard** (still co-located; splitting the shard out for real is Phase 6, once `GameAllocator` has more than one shard to route between) — `GameWebSocketServer`, `AuthService`, `RoomsService`, `LobbyRegistry`, `GameRegistry`, `GameAllocator`.
- **Matchmaker** — its own process, unblocking the Phase 3 coordination question (single active instance, no in-process race possible once it's genuinely the only one).

**Correction (2026-08-10) to this phase's original goal text:** it previously said `AuthService`/`RoomsService` move into the API Gateway. That's no longer accurate — it predates the Phase 1 decision that `createRoom`/`joinRoom` stay on WebSocket. Checked the actual code: `AuthService authService_` and `RoomsService roomsService_` are already members of `GameWebSocketServer` itself (`server/network/websocket_server.hpp`), not `HttpServer`. Both belong with the **WS Gateway**, not the API Gateway.

**Sub-steps:**
- **5.1** — Extract `MatchQueue`/`MatchCreator` interfaces (in-memory default impls only), so `GameWebSocketServer`/`RoomsService`/`Matchmaker` no longer call each other in-process directly. Zero behavior change.
- **5.2** — HTTP-backed implementations (`HttpMatchQueue`/`HttpMatchCreator`) + the two small internal endpoints they call.
- **5.3** — Real separate executables (`api_gateway_main.cpp`/`ws_gateway_main.cpp`/`matchmaker_main.cpp`), Dockerfiles, and running (not just test) services in `docker-compose.yml`.
- **5.4 — done.** Tests for the new pieces + a real end-to-end matchmaking check across actual process/container boundaries.

**Decision Log:**
- **5.1 done.** The in-process coupling was two-directional: `GameWebSocketServer`/`RoomsService` called `Matchmaker::enqueue`/`dequeue` directly; `Matchmaker::tick()` called `GameAllocator::allocate().createMatch(...)` directly — but `GameRegistry` (and the live `GameMatch` it creates) lives in the WS Gateway process, not Matchmaker's. Once Matchmaker is a separate process it can no longer make that call in-process. (Match *discovery* — `attachNewlyMatchedConnections()` polling `gameRegistry_.matchFor(username)` — already goes through shared state, i.e. the Phase 3 `GameIndexStore`, not a direct call, so it needed no change at all.)

Same own-vs-injected pattern used for `LobbyStore`/`GameIndexStore`/`NatsPublisher`: `Matchmaker`'s existing constructor (`GameAllocator&, PlayerAccountStore&, Board, timeoutMs`) is unchanged and now just builds its own `InMemoryMatchCreator` internally — every existing `test_matchmaker.cpp` call site compiled with zero changes. Updated: `server.cpp` (constructs one `InMemoryMatchQueue` wrapping the real `Matchmaker`, passes it to `GameWebSocketServer`), `test_rooms_service.cpp` (5 call sites), `test_websocket_integration.cpp` (9 call sites) — all mechanical, no behavior change, `test_matchmaker.cpp` untouched.

- Verified: `docker compose up --build` and native `ctest`, both green.
- **5.2 done.** Two new internal-only HTTP listeners (`httplib`, same as Phase 1's `HttpServer` — `bind_to_port()`/`listen_after_bind()` on a background thread): `MatchmakerInternalServer` (`server/lobby/`, wraps a real `Matchmaker&`, exposes `POST /internal/queue` and `DELETE /internal/queue/{username}`) and `ShardInternalServer` (`server/matches/`, wraps a `MatchCreator&`, exposes `POST /internal/matches` and `POST /internal/no-match-found`). Two new client-side `MatchQueue`/`MatchCreator` implementations that call them: `HttpMatchQueue` and `HttpMatchCreator`.

Keeps `ShardInternalServer` decoupled from any specific `MatchQueue` implementation.

That line was never actually exercised inside Docker before (the `tests` service only ever ran `KungFuChessServerTests`, never a real server process) — in `docker-compose.yml`, `localhost` doesn't reach the `nats` service at all. Because `NatsPublisher` never throws (by design, Phase 4), this wouldn't have crashed anything — it would have silently no-op'd `GameOverEvent` mirroring for the container's entire lifetime, a hard-to-notice bug. Fixed the same way as the Matchmaker/WS-Gateway addresses: `NATS_URL` env var, default `nats://localhost:4222` (native, unchanged), overridden to `nats://nats:4222` in Compose.

- Found and fixed a real build-performance bug on the first `docker compose up --build` attempt: `tests`/`matchmaker`/`ws-gateway`/`api-gateway` each had an identical `build:` block but no shared `image:` tag, so Compose built **four separate images from scratch** (each a full ~10-minute C++ build, including `FetchContent` of ixwebsocket/hiredis/nats.c) in parallel instead of building once and reusing it. Overwhelmed the Docker daemon (`rpc error: code = Unavailable desc = error reading from server: EOF` after 607s). Fixed by giving all four services the same `image: ctd-server:latest` — Compose now builds once and every service just runs a different `command:` against it.
- **Found and fixed the real root cause of the slow/unstable build, not just its symptom.** The image-sharing fix above stopped Compose from building four separate images, but a single build still took 600s+ and disconnected the daemon again. Root cause: `COMMON_SOURCES` (the shared source list for the three new executables) was listed directly on each `add_executable()` call — CMake compiles each source file separately per target unless told otherwise, so all ~90 shared files (game logic, DB, network, matches, lobby, auth, rooms) were being compiled **three extra times** (once per new executable), on top of `KungFuChessServer`/`KungFuChessServerTests` already compiling them once each — 5x the necessary compilation for a single `docker compose up --build`. Fixed by converting `COMMON_SOURCES` into a CMake `OBJECT` library (`CommonObjects`, compiled once) that `ApiGateway`/`WsGateway`/`MatchmakerServer` each just link against — standard CMake pattern for multiple executables sharing most of their code. (`KungFuChessServer`/`KungFuChessServerTests` left as they already were — this was specifically about the three *new* targets introduced in 5.3a; further consolidating the two original targets onto `CommonObjects` too is a possible future cleanup, not needed to fix this incident.)
- **Docker daemon still disconnected after the OBJECT-library fix** (build time down from 628s to 412s, but still crashing) — same `rpc error: code = Unavailable desc = error reading from server: EOF`, which is a dropped gRPC connection to BuildKit, not a configured timeout. Confirmed the code itself isn't at fault (native build succeeded). ## Phase 6 — Real Game Allocator + multiple shards

**Status:** Done — extended (2026-08-10) past the initial narrow scope to include real in-process multi-shard lookup, see Decision Log.
**Goal:** Implement real allocation logic (load/region-based) inside the seam opened in 0.3 — only meaningful now that more than one shard exists to choose between.
**Decision Log:**
- **Scope decision, made explicit before writing any code:** this phase delivers the actual allocation *decision logic* — `GameAllocator` choosing the least-loaded of several `GameRegistry` shards — because that's precisely what the seam opened in 0.3 and the goal text above ask for. It deliberately does **not** make `GameWebSocketServer` shard-aware (searching for a match across multiple `GameRegistry`s, ticking each one) — that's a materially larger structural change (today `GameWebSocketServer` assumes exactly one `GameRegistry`), and doing it "shortest and fastest" would have meant faking it rather than building it. Named directly rather than silently left out, so it isn't mistaken for "Phase 6 fully matches `Server_Design.md`'s multi-node shard architecture" — it doesn't yet; this is the allocation algorithm alone, proven for real, not a placeholder.
- `GameAllocator` gained a second constructor, `explicit GameAllocator(std::vector<GameRegistry*> shards)`, alongside the original single-registry one (unchanged, still used by every existing call site — `server.cpp`, `ws_gateway_main.cpp`, `Matchmaker`'s default `InMemoryMatchCreator` path, and all three existing `test_game_allocator.cpp` cases — zero edits needed there, same own-vs-injected-shaped no-rewrite guarantee as every other seam this project has touched). `allocate()` now picks `std::min_element` by `GameRegistry::matchCount()` — real load-based selection, not a stub that happens to return the right thing for one shard.
- Constructing a multi-shard `GameAllocator` with an empty vector throws `std::invalid_argument` — an empty shard list has no sensible allocation decision to make, and failing loudly at construction is better than a null-dereference or silent no-op deep inside `allocate()`.
- Tests added: `test_game_allocator.cpp` gained 4 cases (least-loaded selection, rebalancing across two calls, correctly favoring an empty third shard over two already-loaded ones, and the empty-vector constructor throwing) — all pass through the real allocation logic, not mocks.
- **Extended same-day, once asked for something more comprehensive than the narrow first cut:** `GameWebSocketServer` is now genuinely shard-aware, not just `GameAllocator`. New `ShardLookup` interface (`server/matches/shard_lookup.hpp`: `matchFor`/`joinRoom`/`updateAll`) that `GameRegistry` now implements directly (`class GameRegistry : public ShardLookup`) and that a new `ShardRegistry` also implements by linearly searching across N `GameRegistry*` shards and calling `updateAll` on each. `AuthService`, `RoomsService`, and `GameWebSocketServer` changed their lookup-only member from `GameRegistry&` to `ShardLookup&`.
- **Why this was low-risk despite touching three classes:** because `GameRegistry` now *is-a* `ShardLookup`, every single existing call site that passes a concrete `GameRegistry&` (`server.cpp`, `test_auth_service.cpp`, `test_rooms_service.cpp`, `test_websocket_integration.cpp` — none of them touched) keeps compiling unchanged via ordinary C++ reference upcasting. Only `ws_gateway_main.cpp` needed an actual behavioral change, because it's the one place that now constructs more than one shard.
- Deliberately kept `ShardLookup` separate from `GameAllocator` rather than merging lookup into it: `Server_Design.md` §2.d places Game Allocator specifically on the control plane, "not in the hot path of the moves themselves, only in match setup" — `matchFor` is called on every reconnect, which *is* the hot path, so folding it into the allocator would have blurred a distinction the target architecture draws on purpose.
- `ws_gateway_main.cpp` now constructs `SHARD_COUNT` (env var, default 3) independent `GameRegistry` shards, one shared `GameAllocator`/`ShardRegistry` pair over all of them, and passes the `ShardRegistry` (not a single shard) to `GameWebSocketServer`. This is genuinely exercised, not just unit-tested in isolation: a match created via `Matchmaker`'s HTTP round trip can land on any of the 3 shards (whichever `GameAllocator` finds least-loaded), and `attachNewlyMatchedConnections`'s polling loop (`shardRegistry.matchFor(username)`) finds it regardless of which one.
- Tests added: `test_shard_registry.cpp` (6 cases — cross-shard `matchFor`, cross-shard `joinRoom`, both their not-found paths, `updateAll` touching every shard, and the empty-vector constructor throwing).
- **Still explicitly not done, named so it isn't lost:** these are still `SHARD_COUNT` shards living inside *one* `WsGateway` OS process, not separate processes/nodes. Real multi-node sharding needs the routing layer `Server_Design.md` §5 describes (`room_id -> shard` in Redis, reachable across machines) — today's `ShardRegistry` linear search only works because every shard is a plain in-memory object in the same address space. That's a Phase 8-scale (or later) infrastructure step, not a unit of work that fits "fast."
- Verified: native `ctest` and `docker compose up --build` both green.

### Closing the gap against the original requirements (2026-08-11)

A requirements review against the original architecture brief (six components, five technologies, `GameEngine` as sole authority) found that several pieces built and tested earlier in this roadmap were never actually wired into the real running processes — `ApiGateway`/`WsGateway` were still using SQLite, not the `postgres` service already sitting in `docker-compose.yml`; `LobbyRegistry`/`GameIndexStore` were still in-memory in `WsGateway`, not the `RedisLobbyStore`/`RedisGameIndexStore` already built and tested in Phase 3; and "history" (explicitly named in the brief, under both API Gateway and PostgreSQL) didn't exist in any form. Closed all three, scoped to "runs simply on one machine, nothing unnecessary."

**Decision Log:**
- **PostgreSQL wired in for real.** `ApiGateway`/`WsGateway` now use `PostgresPlayerAccountStore` instead of `SqlitePlayerAccountStore` — but only where libpqxx is actually available. New `HAS_POSTGRES` compile definition (`CMakeLists.txt`, set on `CommonObjects` inside the existing `if(PQXX_FOUND)` block) gates `#ifdef HAS_POSTGRES` branches in both `main()` files: `PostgresPlayerAccountStore` + a `postgresConnectionString()` helper (built from `POSTGRES_HOST`/`PORT`/`DB`/`USER`/`PASSWORD` env vars) when defined, `SqlitePlayerAccountStore` otherwise. This is Docker/Linux vs. native Windows in practice (libpqxx isn't installable natively — Phase 2 Decision Log), not a runtime choice. `docker-compose.yml`'s `ws-gateway`/`api-gateway` gained the `POSTGRES_*` env vars and `depends_on: postgres: condition: service_healthy` (required now — `PostgresPlayerAccountStore` throws on connection failure, same as every other required store in this codebase).
- **The `players_db` shared SQLite volume/`working_dir` hack (added in Phase 5.3b) is gone.** It existed only to make two SQLite-backed containers agree on one file — a known limitation flagged explicitly at the time ("acceptable for proving the process split locally, not for production... switching to `PostgresPlayerAccountStore` is a separate decision"). That decision is made now; Postgres itself is the shared store, so the volume/`working_dir` workaround is simply deleted, not replaced.
- **Redis wired in for `LobbyRegistry` and `GameIndexStore` in `WsGateway`.** `ws_gateway_main.cpp` now builds a `RedisLobbyStore` and a `RedisGameIndexStore`, passed to `LobbyRegistry`'s and (each shard's) `GameRegistry`'s injected constructors — both already existed and were tested since Phase 3, just never actually used by a running process.
- **Real design point worked through, not assumed: one `RedisGameIndexStore`, shared across all `SHARD_COUNT` shards.** Since `GameIndexStore::nextGameId()` allocates via Redis `INCR`, sharing one store across shards gives every match a globally-unique `GameId` regardless of which shard created it. That's what makes `ShardRegistry`'s per-shard `matches_.find(gameId)` lookups correct: every shard except the one that actually owns that `GameId` correctly finds nothing, and exactly one finds it. This is precisely the "room_id → shard" routing role `Server_Design.md` §5 describes for Redis, arrived at as a natural consequence of Phase 6's `ShardRegistry` design plus this wiring — not a separate mechanism bolted on.
- **Found and fixed a real latent thread-safety bug while wiring this up.** `RedisGameIndexStore` and `RedisMatchmakerQueueStore` both held a single raw hiredis `redisContext` with no locking. That was safe by accident until now: each was previously only ever reached through a single caller whose own mutex already serialized every call (one `GameRegistry`'s `mutex_`, or `Matchmaker` — actually not even that: `MatchmakerInternalServer`'s HTTP handlers and the main `tick()` loop call `Matchmaker` from different threads with no shared lock, so `RedisMatchmakerQueueStore` was already exposed to genuine concurrent access before this change, just never caught). Sharing one `RedisGameIndexStore` across `SHARD_COUNT` independently-mutexed `GameRegistry` shards makes the same class of race unambiguous and immediate. Fixed both by adding an internal `std::mutex` guarding `context_`, matching the thread-safety `InMemoryGameIndexStore`/`InMemoryMatchmakerQueueStore` already had. `RedisLobbyStore` was checked too — but the "left alone" call made at the time was wrong (see the Docker verification bug list below): `LobbyRegistry` doesn't actually serialize anything itself, and the bug surfaced for real once two WS clients connected to `WsGateway` near-simultaneously.
- **History, from scratch.** New `GameHistoryStore` interface (`recordGame(winner, loser)` / `historyFor(username, limit)`) + `NoOpGameHistoryStore` (default, discards everything — matches `NatsPublisher`'s disconnected-default philosophy) + `PostgresGameHistoryStore` (real, `HAS_POSTGRES`-gated like `PostgresPlayerAccountStore`, one `games` table). Wired into the one place that already has both players' identities at game-end: `RatingUpdater`, which now also calls `historyStore_.recordGame(...)` right after persisting the ELO update — reusing data it already resolves (`usernameForColor` for both colors), rather than adding a parallel subscriber and re-deriving the same thing.
- **Own-vs-injected threaded through the whole chain, preserving every existing call site.** `RatingUpdater` → `GameMatch` → `GameRegistry` → `HttpServer` each gained one additional constructor overload accepting `GameHistoryStore&`, alongside their existing constructor(s) which now default to owning a `NoOpGameHistoryStore` internally. Every pre-existing call site — `test_rating_updater.cpp` (4 cases), `test_game_match.cpp` (6 cases), `test_game_registry.cpp`, `test_websocket_integration.cpp`, `test_rooms_service.cpp`, `server.cpp` — compiled and behaved unchanged. Only `api_gateway_main.cpp` and `ws_gateway_main.cpp` needed real changes, to actually construct and inject a `PostgresGameHistoryStore`.
- **New `GET /players/{username}/history` on `ApiGateway`**, reading from its own `PostgresGameHistoryStore` instance against the same Postgres table `WsGateway`'s instance writes to — this works because Postgres, not either process, is the actual source of truth; `ApiGateway` never calls `recordGame` itself.
- Tests added: `test_no_op_game_history_store.cpp` (1 case), `test_postgres_game_history_store.cpp` (3 cases, gated behind `PQXX_FOUND` like `test_postgres_player_account_store.cpp` — real Postgres, no separate flag needed since libpqxx-availability already implies Docker), a `RatingUpdater` case proving the injected-store constructor actually records, a `GameMatch` case proving the same through a real king-capture end-to-end (same rigor precedent as the Phase 4 NATS test and the Phase 5.4 process-split test), and two `HttpServer` cases (`/history` empty by default, `/history` returns what was recorded).
- Verified: `docker compose up --build` green — **522 test cases / 912 assertions, all passing.** Getting there surfaced five real bugs, all found and fixed during this verification pass rather than assumed away:
  1. **`CREATE TABLE IF NOT EXISTS` race between `ApiGateway` and `WsGateway`.** Both construct their own `PostgresPlayerAccountStore`/`PostgresGameHistoryStore` on startup, and both start concurrently (neither `depends_on` the other) — under Postgres, `IF NOT EXISTS` isn't atomic against a concurrent session doing the same thing, so one process's `CREATE TABLE` occasionally hit `pqxx::unique_violation` on `pg_type` and crashed. Fixed by catching `pqxx::unique_violation` around both `createTableIfMissing()` bodies (`postgres_game_history_store.cpp`, `postgres_player_account_store.cpp`) and treating it as success — a concurrent session already did the work.
  2. **`PostgresGameHistoryStore::historyFor` threw on every row.** `EXTRACT(EPOCH FROM played_at) * 1000` returns a fractional `numeric` (e.g. `1786399397039.490000`); `.as<long long>()` in pqxx rejects the trailing decimal outright. Fixed by casting in SQL: `CAST(EXTRACT(EPOCH FROM played_at) * 1000 AS BIGINT)`.
  3. **Postgres healthcheck raced its own first-time-init sequence.** The `postgres` service had no data volume, so every `docker compose down`+`up` reinitialized from scratch. During that reinit, the official image briefly runs a *temporary* server (Unix socket only, no TCP) to execute init scripts; `pg_isready -U kungfuchess` (no `-h`) connects over that same Unix socket and reports healthy *during that temporary phase* — before the real server is listening on TCP 5432. `ws-gateway`/`api-gateway` were released by `depends_on: service_healthy` right into that gap and got `Connection refused`. Fixed two ways: added a named `postgres_data` volume (subsequent runs skip reinit entirely) and added `-h 127.0.0.1` to the healthcheck (forces a real TCP check, which the temporary server doesn't answer).
  4. **`test_process_split_integration.cpp`'s `waitFor` default (10s) was too tight** for the now much heavier compose stack (Postgres/Redis/NATS/Loki/Promtail all starting alongside `ws-gateway`/`matchmaker`/`tests`), even though `ws-gateway` itself came up fine (confirmed via `docker compose logs ws-gateway` — reached "listening on port 8080" every time). Bumped to 20s.
  5. **The real bug hiding behind #4: `RedisLobbyStore` had no internal locking**, same class of bug as #266 above but missed at the time — `LobbyRegistry` (its only caller) has no mutex of its own, so two WS clients connecting to `WsGateway` close together drove concurrent, unsynchronized calls into the same raw hiredis `redisContext` (undefined behavior in hiredis, not just a logic race). This is almost certainly what made clientB's connection hang in bug #4 even after the timeout bump alone didn't fully explain it. Fixed by adding a `std::mutex` guarding `context_` around all six `RedisLobbyStore` methods, matching `RedisGameIndexStore`/`RedisMatchmakerQueueStore`.

## Phase 8 — Kubernetes (2026-08-11)

Runs the same system as `docker-compose.yml`, but on Kubernetes — the fifth required technology from the original brief. Scoped deliberately narrow: Deployments + Services + liveness/readiness probes (reusing the `/health` endpoints from Phase 7) for all 8 components. No autoscaling/HPA, no Ingress controller, no Agones, no separate namespace — "runs simply on one machine" carried over from the Docker Compose phase. Runtime: Kubernetes built into Docker Desktop (single node, shares the same local image cache as `docker compose build` — no registry push needed).

**Decision Log:**
- **New `k8s/` folder, one file per component** (`postgres.yaml`, `redis.yaml`, `nats.yaml`, `loki.yaml`, `matchmaker.yaml`, `ws-gateway.yaml`, `api-gateway.yaml`), applied with `kubectl apply -f k8s/`. Plus `config.yaml` (one shared `ConfigMap` for non-secret env vars + one `Secret` for `POSTGRES_PASSWORD`, replacing the `environment:` blocks scattered across `docker-compose.yml`) and `promtail-sidecar-config.yaml`.
- **`postgres` gets a `PersistentVolumeClaim`** (`ReadWriteOnce`, `Recreate` deployment strategy so an old and new pod are never both trying to mount it) — same durability fix as the Docker Compose `postgres_data` volume, translated to Kubernetes.
- **Centralized logging redesigned as a sidecar, not a shared volume.** Docker Compose had one `server_logs` volume that `matchmaker`/`ws-gateway`/`api-gateway` all wrote to and one `promtail` container read from — that's a multi-writer access pattern needing `ReadWriteMany` storage, which Docker Desktop's default storage class doesn't provide. Standard Kubernetes fix: each of the three app pods gets a `promtail` sidecar container sharing an `emptyDir` volume with just that pod's own app container — no shared storage needed, `Logger` itself is untouched, and `loki` stays a single central `Deployment`/`Service` exactly as before.
- **No `depends_on` equivalent needed.** `docker-compose.yml` uses `depends_on: condition: service_healthy` to sequence startup; Kubernetes has no direct equivalent. First attempt was an `initContainer` per app pod that polled the dependency's port before letting the main container start (`busybox` + `nc`) — mirrors compose's behavior exactly, but hit a real, environment-specific failure (see bug #1 below) and was removed in favor of relying on the fact that `MatchmakerServer`/`WsGateway`/`ApiGateway` already throw and exit if a dependency isn't reachable at startup (true since Phase 2/3) — `restartPolicy: Always` (Kubernetes' default) retries with backoff until dependencies are up. Simpler, one fewer moving part, no extra image to pull.
- Verified: all 8 pods `Running` (matchmaker/ws-gateway/api-gateway `2/2` — app + promtail sidecar), `curl http://localhost:8081/health` and `:8082/health` both `200` through Docker Desktop's `LoadBalancer` port mapping to `localhost`. Two real bugs found and fixed getting there:
  1. **`busybox:1.36` failed to pull** — `Init:ErrImagePull`, traced via `kubectl describe pod` to `failed to resolve reference ... 500 Internal Server Error` from Docker Desktop's local registry mirror, specific to that image/tag (`postgres`/`redis`/`nats`/`loki` all pulled fine via the same mirror). Root-caused as an unnecessary dependency rather than patched around: removed the `initContainer` entirely (see Decision Log above) instead of chasing a working `busybox` tag.
  2. **Every `promtail` sidecar crash-looped** (`Unable to parse config: /etc/promtail/config.yml does not exist`) — the `ConfigMap` data key was `promtail-config.yml`, but a `ConfigMap` volume mount creates a file named after its *key*, and the sidecar's `-config.file` arg pointed at `/etc/promtail/config.yml` (no `promtail-` prefix) — a naming mismatch, not a missing mount. Fixed by renaming the `ConfigMap` key to `config.yml` to match the arg.

### Rooms over REST (2026-08-11)

Closes the last explicitly-deferred gap from Phase 1's Decision Log: `createRoom`/`joinRoom` were WebSocket-only because, at the time, they seemed to need a live connection to attach to. They don't — `GameRegistry::createRoom`/`joinRoom` only ever register a username against a `GameId` in `indexStore_`; attaching a socket is a separate step (`GameWebSocketServer::attachToMatch`) that already happens automatically on WS login via the existing resume path (`AuthService::login` → `gameRegistry_.matchFor(username)`). So a REST-created/joined room is picked up for free the next time that username logs in over WebSocket — no changes needed to the login/resume flow at all.

**Decision Log:**
- **New `RoomsClient` interface** (`server/rooms/rooms_client.hpp`) + `NoOpRoomsClient` (safe default, every call fails) + `HttpRoomsClient` (real, calls `WsGateway`'s internal API) — same shape as `MatchCreator`/`MatchQueue` for the existing Matchmaker↔WsGateway split.
- **REST lives on `ApiGateway`, not `WsGateway`**, matching the original 6-component brief (API Gateway = REST surface). `POST /rooms` and `POST /rooms/{roomCode}/join` on `HttpServer` proxy to two new internal routes on `WsGateway`'s `ShardInternalServer` (`POST /internal/rooms`, `POST /internal/rooms/{roomCode}/join`), which call straight into `RoomsService` — the same pattern `HttpMatchCreator`/`MatchmakerServer` already established for match creation.
- **`ws_gateway_main.cpp` builds a second, independent `RoomsService`** just for `ShardInternalServer`, instead of threading a reference through `GameWebSocketServer`'s constructor. Safe because `RoomsService` is a stateless facade over `shardRegistry`/`gameAllocator`/`accounts`/`matchQueue` (all shared, real state) plus its own copy of `templateBoard` (plain data) — two instances wrapping the same underlying registries behave identically to one shared instance.
- **Own-vs-injected threaded through again**: `HttpServer` gained a 4th constructor (`GameHistoryStore&` + `RoomsClient&`); every pre-existing call site (`server.cpp`, `api_gateway_main.cpp`'s old 2-/3-arg paths, all pre-existing `test_http_server.cpp` cases) kept compiling unchanged. `ShardInternalServer` gained a mandatory `RoomsService&` parameter (no default — `MatchCreator&` already wasn't optional either), so its ~6 existing test call sites were updated to construct a real `RoomsService` (`GameRegistry`/`GameAllocator`/`Matchmaker`/`InMemoryMatchQueue`, same scaffolding `test_rooms_service.cpp` already used).
- **Coverage audit requested explicitly** ("full coverage, no unused code") surfaced 8 untested branches, all closed: missing-username-400 and malformed-JSON-400 on both new endpoints at both layers (internal + public), plus `HttpRoomsClient::joinRoom` against an unreachable server and `HttpRoomsClient::createRoom` against a real non-201 response (distinct from "unreachable"). Left deliberately untested: the `json::parse_error` catch blocks around parsing our *own* server's response bodies — reaching them needs a deliberately-malformed-JSON fake server, and no other HTTP client in this codebase (`HttpMatchCreator`) tests that branch either, so it would be new depth rather than matching an established bar.
- **Unrelated bug found during this verification pass**: `test_nats_publisher_integration.cpp`'s round-trip wait was `natsSubscription_NextMsg(..., 2000)` — under the now-much-heavier compose stack (same root cause as the Phase 8 process-split timeout fix), this occasionally hit `NATS_TIMEOUT` (status 26). Bumped to 5000ms.
- Verified: `docker compose up --build` green — **543 test cases / 976 assertions, all passing.**
